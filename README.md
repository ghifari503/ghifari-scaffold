# Project Scaffold (Codex/GPT + Claude + Gemini Compatible)

This package helps a solo founder or owner run AI agents safely for both new projects from scratch and existing or inherited projects.

Use this scaffold when:
- you want to define and bootstrap a new project from zero
- the product already exists
- the codebase was started by someone else
- the repository already has its own framework, dependencies, or conventions
- you want structured discovery, onboarding, incremental feature delivery, QA, release support, and developer-to-developer continuity
- you may need redesign, UI revamp, flow changes, refactor, migration, or architecture cleanup inside an existing product

## Main Components
- `AGENTS.md`: single source of truth for Codex/GPT, Claude, and Gemini runtime instructions
- `SCAFFOLD_WORKFLOW.md`: concise end-to-end workflow guide for developers and AI contributors
- `docs/DEVELOPMENT_WORKSPACE.md`: safe layout and startup behavior for the local `development/` workspace
- `CLAUDE.md`: Claude compatibility pointer to `AGENTS.md`
- `GEMINI.md`: Gemini compatibility pointer to `AGENTS.md`
- `COMMANDS.md`: canonical command list and prompt menu
- `guardrails/system/SKILL_CATALOG.md`: shared runtime skill catalog regenerated by `cek skill`
- `docs/`: overview and navigation entrypoints
- `guardrails/`: strict rules, policies, protocols, standards, and guides
- `guardrails/flutter/`: Flutter/Dart development, QA, and release safety policy
- `artifacts/`: project state, outputs, logs, decisions, and evidence
- `artifacts/access/README.md`: local/dev/demo URLs and approved non-production access inventory
- `artifacts/docker/`: Docker-specific notes, logs, smoke evidence, and environment mapping
- `artifacts/flutter/`: Flutter intake checklist and future Flutter-specific evidence
- `guardrails/memory/` and `artifacts/memory/`: local auditable memory for continuity across sessions, maintained by `memory-curator`
- `artifacts/memory/FEATURE_REGISTRY.toml`: structured feature/module status, dependency, impacted-system, risk, test, and release registry
- `.claude/skills/`: Claude-compatible workflow skills
- `.codex/skills/`: Codex-preferred workflow skills
- `.agents/rules/` and `.agents/skills/`: Antigravity workspace rule entrypoints and synchronized skills
- Missing local skills: use `find-skills`, validate the candidate, then install approved skills into both runtime folders and run `cek skill`
- `.claude/agents/` and `.codex/agents/`: specialized agents
- `templates/`: artifact templates
- `workflows/`: recommended execution flows

## Operating Principle
- Start with `start`. The scaffold routes work from the state of `development/`:
  - zero target-project folders, excluding scaffold defaults: Greenfield Discovery for a new project from scratch
  - one or more target-project folders: existing/inherited-project selection and intake
- `start` selects a route only. It never authorizes framework bootstrap, dependency installation, database creation, code generation, or product code.
- Greenfield projects use `G0-G5`: route, founder discovery, minimum first-feature requirements, architecture/bootstrap plan, pre-coding gate, then one approved first slice.
- Existing projects start with repo intake, architecture/stack audit, and `I2 Impact Scan` for the requested change.
- Preserve existing architecture, framework, and coding conventions unless the founder approves a change.
- Prefer incremental updates over full rewrites.
- Frontend behavior should still be validated before backend contract expansion when UI is part of the scope.
- For existing-project onboarding, clone or attach the target repository into `development/[project-folder]`; that folder becomes the active workspace for the cloned project.
- Target repositories and new project folders live under `development/[project-folder]`.
- Each target project is a separate Git repository. Commit and push project source plus `artifacts/shared/` from inside that project folder, never from the scaffold root.
- Existing Flutter projects are supported through intake and Flutter-specific guardrails; do not bootstrap a new Flutter app before the target repo is audited.

## Recommended First Run
1. Read `AGENTS.md`, then send `start`.
2. When `development/` is empty, provide project name, intended outcome, first feature candidate, constraints, and available references. The agent creates the project charter and minimum baseline before proposing a bootstrap plan.
3. When `development/` contains a project, choose the target. The agent performs `I1` intake, learns the current system, then performs `I2` only for a requested change.
4. Review the compact plan for every medium or major activity and provide explicit approval before execution.
5. Build, QA, and release only the approved feature/module slice.

## Workflow Policy
- One feature and one selected task slice per session by default.
- Existing project first: discover what already exists before proposing structural changes.
- Greenfield first: define only the first approved feature and its required foundation before creating source code.
- Incremental by default: update only impacted artifacts, modules, pages, tests, and contracts.
- Broad changes are allowed when they are explicitly scoped and approved, for example:
  - redesign or UI revamp
  - user flow changes
  - module refactor
  - architecture cleanup or migration
- Architecture changes require explicit founder approval.
- Framework changes require explicit founder approval.
- Broad rewrites require a dedicated decision log entry in `artifacts/architecture/DECISION_LOG.md`.
- Persistent memory is advisory: use it for recall and handoff, but verify it against current repo evidence, founder decisions, and active gate files before acting.
- Memory uses a hybrid format: Markdown for reviewable policy and summaries, `artifacts/memory/MEMORY_LEDGER.toml` for structured agent updates.
- Feature/module status uses the same pattern: `FEATURE_REGISTRY.toml` for structured updates and `FEATURE_REGISTRY.md` for founder-readable review.

## Continuity And Project Baseline
- Every target project keeps Git-carried continuity under `development/[project-folder]/artifacts/shared/`.
- `PROJECT_STATE.md` records the project baseline, `ACTIVE_CONTEXT.md` records current work, `CONTRIBUTOR_LOG.md` records contributor-session detail, and `handoffs/` holds incomplete-slice handoffs.
- The scaffold-wide `artifacts/operations/AGENT_ACTIVITY_LOG.md` records which agent performed which task category and activity across projects. Activity logging is event-based and token-aware: agents read only its current snapshot and relevant recent entries, never the whole log or per-tool-call history.
- For an inherited project without usable documentation, the agent first asks whether references exist. If none do, it creates a source-linked, code-derived `PROJECT_STATE.md` baseline and synchronizes verified facts to scaffold memory and the feature registry.
- Future agents read shared project context and relevant memory before scanning source, then use targeted paths instead of relearning the entire repository.

## QA With Efficient Context Use
- QA defaults to the smallest impact-scoped check that covers the changed behavior.
- A full or broad suite requires a recorded reason, such as a release gate, cross-module risk, or inability to target the test runner.
- QA records `last_passing_point`, the delta since that point, concise result summaries, and durable evidence paths instead of long raw logs.
- Manual visual QA is explicitly requested when human judgment is needed for UI, layout, responsive behavior, rendered documents, charts, canvas, or browser-visible flows.

## Compatibility Notes
- Codex/GPT, Claude, and Gemini flow: read `AGENTS.md` first.
- `CLAUDE.md` and `GEMINI.md` are compatibility pointers only.
- Antigravity setup and its Gemini model-routing limits are documented in `docs/ANTIGRAVITY_SETUP.md` and `guardrails/system/ANTIGRAVITY_RUNTIME_POLICY.md`.
- For strict same process/output across Codex/GPT, Claude, and Gemini, enforce `guardrails/system/RUNTIME_PARITY_CONTRACT.md`.
- Keep both `.claude/` and `.codex/` paths unless you intentionally migrate and update the references.
- Run `cek skill` after adding or renaming runtime skills so prefixes and catalog stay synchronized.
- External skill discovery uses `find-skills`; automatic acquisition is limited to the allowlisted publishers in `guardrails/system/SKILL_CHECK_POLICY.md`.
- Protected scaffold flow changes follow `guardrails/system/SCAFFOLD_CORE_CHANGE_POLICY.md` and require maintainer review.
- This scaffold is licensed for authorized internal Odonplay use under `LICENSE.md`.

## Git Hygiene
- `.gitignore` keeps secrets, local dependencies, build output, raw Playwright artifacts, caches, logs, and editor files out of the scaffold repository.
- The scaffold repository ignores all target project files under `development/[project-folder]/`, including `artifacts/shared/`. The target project's own Git repository tracks its source and shared continuity together.
- `development/_project-template/artifacts/shared/` provides the default shared-context structure for each new or attached target project.
- After cloning the scaffold, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\enable-scaffold-git-protection.ps1` once. Root scaffold commit and push are blocked unless a maintainer uses the explicit `ALLOW_SCAFFOLD_COMMIT=1` or `ALLOW_SCAFFOLD_PUSH=1` override.
- Apply the GitHub `main` Ruleset in `docs/REPOSITORY_GOVERNANCE.md`: only `@odonplay` may update `main`; all other contributors use pull requests.

## Codex Model Routing
- For a new Codex CLI session, use `scripts/codex-route.ps1 --dry-run "[task]"` first. The router selects Luna/`fast`, Terra/`standard`, Sol/`deep`, or Sol/`critical` from complexity, risk, required accuracy, and relative token/cost bands. Terra is the daily-development default.
- The Terra supervisor runs routing automatically for coding work. It continues `standard` work itself and delegates Luna/Sol work through one ephemeral worker; user model selection is not required. The router cannot replace the model of an active chat.
- Use `--legacy-5-5` only for explicit legacy reproduction or benchmarking. It is not an automatic fallback.
- Each developer may override unavailable model IDs in `~/.codex/model-routing.local.json` or `CODEX_ROUTING_CONFIG`; this local file is intentionally ignored by Git.
- See `guardrails/system/MODEL_ROUTING_POLICY.md` for escalation, fallback, and Git-safe Token & Cost Monitor rules.
- Keep documentation, guardrails, templates, runtime skills, memory, and operational Markdown artifacts version controlled when this scaffold is initialized as a Git repository.

## Claude Code VS Code Routing
- Claude Code in VS Code starts new project sessions on Sonnet and routes bounded subtasks automatically through native Haiku or Opus subagents when the policy permits. See `guardrails/system/CLAUDE_VSCODE_MODEL_ROUTING_POLICY.md` and `docs/CLAUDE_CODE_VSCODE_SETUP.md`.
- The visible session model remains sticky. VS Code `Auto` is a permission mode, not a model router. Fable is used only when a developer-local or managed configuration verifies an actual supported model ID or alias.
